# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Public site + admin backoffice for "Pasticceria Cuciniello", a Naples pastry shop. Customers browse a
catalog (specialties, panettoni, custom cakes) and submit pickup bookings; an admin backoffice manages
bookings and the catalog. Built with TanStack Start (React 19) on Supabase (Postgres + Auth + Storage),
deployed to Vercel via Nitro. Originated from Lovable (see "Lovable platform" below).

## Commands

Package manager is **bun** (`bun.lock`, `bunfig.toml` — do not use npm/yarn/pnpm lockfiles).

- `bun install` — install deps. `bunfig.toml` enforces a 24h supply-chain guard (`minimumReleaseAge`) on
  new package versions; adding a package to `minimumReleaseAgeExcludes` needs explicit user confirmation.
- `bun run dev` — start the dev server (`vite dev`).
- `bun run build` — production build (`vite build`, Nitro/vercel preset).
- `bun run lint` — `eslint .`. This also enforces Prettier formatting as lint **errors** (via
  `eslint-plugin-prettier`), not just style warnings — run `bun run format` first if lint is noisy.
- `bun run format` — `prettier --write .`.
- `npx tsc --noEmit` — typecheck (no dedicated script in `package.json`, but this is the standard check).
- No test framework is configured in this repo.

## Routing

File-based routing via TanStack Router under `src/routes/` (see `src/routes/README.md` for the full
convention table). Key points:
- `__root.tsx` is the app shell (wraps every page, owns the 404/error boundary).
- `routeTree.gen.ts` is auto-generated — never hand-edit it; it's regenerated by the router plugin on
  dev/build and must be committed in sync with route file changes or routes 404 in production.
- `_authenticated/route.tsx` is a layout route: its `beforeLoad` checks `supabase.auth.getUser()` and
  redirects to `/auth` if there's no session. Everything under `src/routes/_authenticated/` (dashboard,
  catalogo, prenotazioni/$id) is backoffice-only and requires a logged-in Supabase user.
- Public pages live directly under `src/routes/`: `/`, `/specialita` (vetrina), `/panettoni`, `/prenota`
  (standard tray booking), `/torta-personalizzata` (multi-step custom cake wizard), `/grazie`, `/auth`.

## Server functions & the two Supabase clients

Backend logic lives in `src/lib/*.functions.ts` as `createServerFn` handlers (TanStack Start). There are
two distinct ways a handler talks to Supabase — picking the wrong one silently breaks RLS assumptions:

1. **`publicClient()`** (defined locally in each `*.functions.ts` file) — uses the anon/publishable key,
   no user session. Used for public reads (catalog, ordering status) and for `createBooking`, which is
   deliberately anonymous. Every table/action reachable this way must have an explicit `anon` RLS policy.
2. **`requireSupabaseAuth` middleware** (`src/integrations/supabase/auth-middleware.ts`, auto-generated —
   do not edit directly) — validates the caller's Bearer JWT and injects `context.supabase` (a client
   scoped to that user's session) and `context.userId`. Admin-only server functions attach this
   middleware, then explicitly check `context.supabase.rpc("has_role", { _user_id, _role: "admin" })`
   and `throw new Error("Forbidden")` if false. **This app-level check is a UX nicety layered on top of
   Postgres RLS, not a substitute for it** — RLS policies are the actual security boundary.

`src/integrations/supabase/client.ts` (also auto-generated, do not edit) is the browser-side client used
directly in route components for auth calls (`supabase.auth.getUser()`, `signOut()`, etc.).

## Supabase: RLS, migrations, generated types

- Authorization model: `app_role` enum (`admin`/`staff`), `user_roles` table, and a `has_role()` SQL
  `SECURITY DEFINER` function used inside RLS policies. The **first** user ever created is
  auto-promoted to admin by a trigger on `auth.users` insert (`handle_new_user_bootstrap`); `EXECUTE` on
  that function and on `has_role` is revoked from `anon`.
- **RLS gotcha to remember**: `.insert(...).select(...)` becomes `INSERT ... RETURNING` under the hood.
  Postgres requires the table's **SELECT** policy (not just the INSERT `WITH CHECK`) to permit the
  acting role for `RETURNING` to succeed. `bookings` has no SELECT policy for `anon`, so
  `createBooking` generates the row id client-side and skips `.select()` entirely rather than reading
  the inserted row back.
- Migrations in `supabase/migrations/*.sql` are plain files — a migration existing in the repo does
  **not** mean it's been applied to the live database; those are separate steps. When working against
  the live project (via the Supabase MCP tools), check `list_migrations` before assuming schema state,
  and use `apply_migration` to actually run a new one.
- After any schema change, regenerate `src/integrations/supabase/types.ts` (via the Supabase MCP
  `generate_typescript_types` tool or the Supabase CLI) — never hand-edit this file.

## Domain model

- `bookings`: `booking_type` enum (`standard` | `torta_personalizzata` | `panettone`), `booking_status`
  enum (`da_preparare` | `pronto` | `ritirato` | `annullato`). `items` (standard/panettone cart) and
  `cake_config` (custom cake spec) are JSONB, shaped by the zod schemas in `bookings.functions.ts`.
- `ordering_status` is a singleton table (one row, `id boolean primary key`) with a per-category enabled
  flag (`standard_enabled`, `torta_personalizzata_enabled`, `panettone_enabled`) used to pause new
  bookings for a category from the admin dashboard. This is enforced **both** in the UI (banners,
  disabled submit) **and** inside `createBooking` server-side — don't remove the server-side check when
  touching booking flows.
- Catalog tables: `specialties`, `panettoni`, `cake_bases`, `cake_fillings`, `cake_sizes`. Products carry
  a nullable `quantity` (stock); `quantity = 0` hides the item from public catalog reads, `NULL` means
  unlimited. Product photos go to the Supabase Storage bucket `product-images` (public read, admin-only
  write via RLS) — only the public URL is stored in `image_url`, never binary data in Postgres.

## WhatsApp handoff

Bookings are confirmed by deep-linking to WhatsApp (`src/lib/whatsapp.ts`). The booking submit handlers
call `openWhatsAppPlaceholder()` **synchronously inside the click handler, before any `await`**, then
`deliverWhatsAppMessage()` redirects that already-open tab once the async booking save resolves. Do not
reorder this — opening the tab after an `await` gets it blocked by popup blockers since it's no longer
tied to a user gesture.

reached production.
